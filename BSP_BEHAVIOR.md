# Поведение обмена БСП: как исполняются правила обмена (КД 2.0)

> Загрузить в «Знания» Open WebUI вместе с [KNOWLEDGE.md](KNOWLEDGE.md).
> База знаний — о том, как читать правила инструментами. Этот справочник — о
> том, как правила **исполняются**: что делает с ними библиотека стандартных
> подсистем (БСП) при обмене через план обмена. Нужен, когда спрашивают «почему
> задвоилось», «почему не пришло», «почему не провёлся», «почему ветка не
> работает».

**Откуда факты.** Перенесено и сокращено из справочников проекта
[kd2-rules-mcp](https://github.com/egordoronchenko/kd2-rules-mcp) (Егор Доронченко,
лицензия MIT): там каждое утверждение подтверждено строками кода исполнителя БСП
3.1.12 (обработка «Конвертация объектов информационных баз»), часть — живым
обменом между тестовыми базами. Утверждения раздела 1 мы дополнительно сверили с
кодом БСП 2.3: совпадают. Пометка **(вывод)** — следует из кода, живым обменом не
проверялось. Пометка **(зависит от версии БСП)** — в 2.3 и 3.1 поведение разное.

Версия БСП в УПП старая, в ЕРП и Рознице новая. Если вывод держится на пункте с
пометкой «зависит от версии», так и скажи человеку.

## 1. Ветки выгрузки при обмене через план обмена

Проверено по коду БСП 2.3 и 3.1.

- **Выгружается только очередь узла.** БСП берёт из плана обмена объекты,
  зарегистрированные на узле, и для каждого ищет ветку выгрузки **по его типу**.
  Ветка — это пропуск типа в выгрузку плюс обработчики, а не выборка данных.
- **Объект выборки ветки — пусковой тип, а не декорация.** Ветку запускают
  объекты этого типа из очереди. Если объекта нет ни в правилах регистрации, ни
  в составе плана, ветка при обмене через план не срабатывает никогда.
  `trace_document` пишет это в поле «регистрация», `check_rules` — проверка
  «объект не регистрируется».
- **Способ отбора «произвольный алгоритм» не исполняется.** Выборка, которую
  задаёт обработчик «перед обработкой правила», не используется. Сам обработчик
  выполняется: один раз перед первым объектом этого типа в очереди. Он может
  выгружать данные своим запросом — так устроены ветки ввода остатков.
  Произвольный алгоритм исполняется только при ручном обмене универсальной
  обработкой.
- **«Отказ» в «перед обработкой правила» ничего не отменяет.** БСП его не
  проверяет: код после него выполняется, объекты из очереди выгружаются. Многие
  ветки начинаются с «Отказ = Истина» — это рассчитано на универсальную
  обработку, при обмене через план ветка работает.
- **«Отказ» в «перед выгрузкой объекта» работает**: объект не выгружается.
  Раньше обработчика ветки срабатывает общий обработчик конвертации «перед
  выгрузкой объекта». Его отказ снимает объект для любой ветки, и обработчик ветки
  тогда не вызывается. `trace_document` показывает, есть ли общие обработчики.
- **Для типа работает первая включённая ветка.** Вторая ветка на тот же тип
  молча не используется. `check_rules`: «вторая ветка на тот же объект».
- **Отключение группы правил не действует.** БСП читает ветки, правила
  конвертации и правила регистрации, не глядя на группы, в которых они лежат.
  Отключённым считается только само правило. У групп свойств внутри правила
  конвертации (табличных частей) отключение действует.
- **Правило регистрации без признака «валидное» не загружается вовсе.**
- **Порядок веток** в правилах на выгрузку не влияет, кроме выбора первой ветки
  для типа.

## 2. Где исполняются обработчики

- **Обработчики загрузки приёмник берёт из своей копии правил отправителя** —
  из правил корреспондента, загруженных в приёмник, а не из правил, пришедших в
  сообщении. Проверено живым обменом. Следствие: правка правил отправителя без
  перезагрузки комплекта в приёмник на загрузку не влияет. Ошибка загрузки
  правится в правилах отправителя **и** в копии у приёмника, загружаются оба
  комплекта. Исключение — обмен через внешнее соединение.
- **Код обработчиков выгрузки исполняется в источнике**, загрузки — в
  приёмнике. Процедуры общих модулей, которые зовёт обработчик, читай в той
  конфигурации, где он выполняется.
- **Алгоритмы делятся по режиму.** Алгоритм с признаком «используется при
  загрузке» есть только при загрузке, остальные — только при выгрузке. Обращение
  к алгоритму другого режима падает так же, как обращение к несуществующему.
  `check_rules`: «нет алгоритма», «алгоритм другого режима».
- **Ошибка в любом обработчике** пишется в протокол обмена. Если в настройках
  обмена не включено «продолжать при ошибке», выгрузка или загрузка прерывается
  целиком, и сообщение не формируется.

## 3. Объект по ссылке: целиком или только ссылкой

Значение реквизита-ссылки (контрагент в документе, номенклатура в строке)
уходит в сообщение одним из двух способов.

- **По умолчанию — только ссылкой**: в сообщение пишутся лишь поля поиска
  объекта. Остальные реквизиты его правила конвертации **не исполняются**, и
  правка их соответствий ничего не меняет в приёмнике.
- **Целиком** объект уходит, если:
  - у объекта своя ветка выгрузки и он попал в очередь;
  - обработчик реквизита («перед выгрузкой» или «при выгрузке») ставит
    «ВыгрузитьОбъект = Истина»;
  - код явно вызывает «ВыгрузитьПоПравилу» для этого объекта (часто через общий
    алгоритм вроде «ВыгрузитьНоменклатуру»);
  - у правила регистрации объекта задан реквизит узла с режимом выгрузки, на узле
    стоит «при необходимости» (или пусто), и объекта ещё нет в регистре
    соответствий для этого узла. Тогда он уходит целиком при первой ссылке.
    `trace_document` показывает этот реквизит в регистрации.
- Для классификаторов и справочников, которые приёмник находит по полям поиска
  (организации, валюты), «только ссылкой» — штатная схема. Для справочника,
  который должен прийти с заполненными реквизитами, — причина «пришёл пустым».
  `check_rules`: «только ссылкой».
- **Реквизит молча не приходит**, ошибок в протоколе нет: у реквизита не указано
  правило конвертации, а правила для типа значения в правилах нет — значение не
  выгружается. Если правило не указано, БСП берёт **последнее** правило
  конвертации с таким источником.
- **Правило, на которое никто не ссылается**, не исполняется. Исключение —
  подбор по типу из предыдущего пункта. `check_rules`: «правило не вызывается»,
  с пометкой, если правило последнее для своего источника.

## 4. Поиск объекта в приёмнике: дубли и слияние

### Как ищет приёмник (по шагам, переход дальше — если не нашёл)

1. Регистр соответствий объектов — если отправитель передал идентификатор
   (признак правила «синхронизация по идентификатору»). Объект, найденный однажды
   по полям, со следующего обмена находится уже здесь.
2. Имя предопределённого элемента.
3. По идентификатору. Не нашли — без признака «продолжать поиск по полям»
   поиск на этом **кончается**: создаётся новый объект с идентификатором источника
   (или пропуск при «не создавать, если не найден»).
4. Обработчик поиска («ПоследовательностьПолейПоиска») — варианты наборов полей.
5. Без обработчика — один поиск по всем полям поиска.
6. Не нашли — создаётся новый объект, если нет «не создавать, если не найден».

- В сообщение со ссылкой уходят **только поля поиска** правила. «Поиск» и
  «Обязательное» у реквизита для БСП одно и то же.
- Поиск — запрос «где поле1 = значение1 и поле2 = значение2…», берётся **первая
  строка без упорядочивания**. Строки сравниваются на точное равенство.
- Обработчик поиска выполняется в приёмнике, из копии правил у приёмника. Дойдёт
  ли до него дело, решает отправитель: передал ли идентификатор и признак
  продолжения поиска. Читается через `get_rule_handler` по правилу
  конвертации, обработчик «ПоследовательностьПолейПоиска».

### Типовые случаи

| Симптом | Причина | Как проверить |
|---|---|---|
| Новый экземпляр при каждом обмене | У правила нет ни синхронизации по идентификатору, ни полей поиска, ни обработчика поиска — искать нечем | `check_rules`: «поиск: нет ключей»; `get_conversion_rule` — признаки и поля поиска |
| Дубль при совпадающих ИНН и КПП | Наименование среди полей поиска: в двух базах его пишут по-разному (кавычки, порядок слов, форма собственности) — одно расхождение, и объект не найден **(вывод)** | `get_conversion_rule` — поля поиска; обработчик поиска — какие поля в вариантах |
| Обработчик поиска «должен» искать по ИНН + КПП для юрлиц, а срабатывает ветка «параметров нет» | Обработчик читает параметр объекта, а реквизит передаёт его без признака поиска: такой параметр приходит уже после поиска. Проверено живым обменом | `check_rules`: «поиск: параметр без признака поиска», «поиск: параметр не передаётся» |
| Разные объекты источника «находят» один объект приёмника и по очереди его перезаписывают | Из условия поиска осталось одно «ЭтоГруппа»: других полей поиска нет, или обработчик называет поля, которые не помечены признаком поиска, — такие имена молча выпадают **(вывод)** | `check_rules`: «поиск: ключ только ЭтоГруппа», «поиск: имя не из полей поиска» |
| Объект связался с чужим объектом без ИНН; документы «висят» не на том контрагенте | Поиск по ИНН без проверки, что ИНН заполнен: пустой ИНН находит первый попавшийся объект с пустым ИНН | Обработчик поиска — есть ли проверка заполненности ИНН перед вариантом без наименования |
| Обработчик поиска написан, но не работает | Включена синхронизация по идентификатору без «продолжать поиск по полям» — до обработчика дело не доходит | `check_rules`: «поиск: обработчик не вызывается» |
| После неудачи по идентификатору всё равно создаётся новый | Продолжение поиска включено, а полей поиска и обработчика нет | `check_rules`: «поиск: продолжение без полей» |

- **Варианты поиска в обработчике должны различаться.** БСП вызывает обработчик
  с номером варианта 1, 2… до 10 и ищет, только пока он возвращает **новый**
  набор полей. Обработчик, который не смотрит на номер варианта, даёт одну попытку.
  Пустой набор в первом вызове — поиск по всем полям поиска; со второго вызова
  несработавшая ветка оставляет прошлый набор, и перебор кончается.
- Типовой образец для контрагентов: при заполненном ИНН — 1) ИНН, КПП,
  Наименование; 2) ИНН, КПП; 3) ИНН, Наименование; без ИНН — Наименование.

## 5. Признаки правила конвертации — что делают в БСП

`get_conversion_rule` показывает их в поле «признаки».

| Признак | Что делает |
|---|---|
| синхронизация по идентификатору | Отправитель передаёт идентификатор; приёмник ищет по регистру соответствий, затем по идентификатору; новый объект получает идентификатор источника |
| продолжать поиск по полям, если по идентификатору не нашли | Без него не найденный по идентификатору объект сразу создаётся, до полей и обработчика поиска дело не доходит |
| не создавать, если не найден | Не найденный объект не создаётся и пропускается. Для значения-ссылки с идентификатором не действует: приходит ссылка с идентификатором источника |
| не замещать найденный объект | Найденный объект не перезаписывается целиком (обработчик «при загрузке» может это отменить); не найденный создаётся. Тот же признак у реквизита — не перезаписывать только этот реквизит |
| новый номер или код, если не указан | Пустой номер или код получает новое значение перед записью |
| не запоминать выгруженные | Влияет только на объект, ссылающийся на самого себя |
| при переносе по ссылке — только идентификатор | Не опирайся на него: поведение для ссылки с идентификатором зашито в код БСП (проверено по 2.3 и 3.1) |
| не выгружать объекты свойств по ссылкам | **(зависит от версии БСП)** В 2.3 объекты из реквизитов уходят только ссылкой; в 3.1, по данным kd2-rules-mcp, признак читается и не действует |
| выгружать только при наличии ссылки | БСП не читает (2.3 и 3.1) |

## 6. Загрузка: ошибки, транзакции, проведение

- **После ошибки обмена часть объектов уже в приёмнике.** Транзакцией загрузки
  управляет константа приёмника «количество элементов в транзакции загрузки
  данных»:
  - 1 — каждый объект пишется сам и не откатывается;
  - 0 — всё сообщение одной транзакцией, откат целиком;
  - N — фиксация каждые N объектов.

  Включённое «продолжать при ошибке» выключает транзакции. Жалобу «задвоилось
  после сбоя» разбирай с учётом того, что неудачная попытка уже могла создать
  объекты.
- **Документ пришёл, но не проведён, ошибок в протоколе нет.** Документ пишется
  непроведённым и встаёт в очередь отложенного проведения. Очередь проводится
  после загрузки всего сообщения. Возможные причины:
  - Проведение не прошло (ошибка или не прошла проверка заполнения). Тогда в
    журнале регистрации приёмника — «Не удалось провести документ…», в
    результатах обмена — «Непроведенный документ». Прежние движения уже удалены.
  - Загрузка сообщения упала, и очередь не проводилась.
  - У правила нет включённого реквизита «Проведен». Новый документ остаётся
    непроведённым **(вывод)**.
  - Режим задан явно в обработчиках («РежимЗаписи», «Объект.Проведен»).
- **Обработчик сам пишет объект в «после загрузки»** («Объект.Записать(»):
  запись идёт до установки режима загрузки. Документ проводится с полной логикой,
  потом БСП распроводит его и ставит в очередь — проведение дважды, или ошибка и
  откат всего сообщения **(вывод)**. `check_rules`: «запись объекта после
  загрузки».
- **Обработчик падает в новой базе приёмника** («Преобразование значения к типу
  Булево не может быть выполнено»), а в рабочей те же правила работают.
  Обработчик читает реквизиты пустой ссылки (шаблона, вида документа) и проверяет
  «Если Реквизиты.Флаг Тогда». В рабочей базе эти настройки заполнены, в новой —
  нет.

## 7. Перечисления, удаление, регистрация, загрузка правил

- **Перечисление: результат обмена «Ошибка», в протоколе код 71** («Не найдено
  соответствие для значения Источника»). Для значения перечисления источника нет
  соответствия значений. Типично после добавления значения в перечисление
  источника. Соответствие применяет только отправитель.
- **В приёмнике объект удалился, а не пометился.** Приёмник находит объект по
  идентификатору из сообщения об удалении и удаляет его непосредственно. Пометку
  вместо удаления делает событие конвертации «при получении информации об
  удалении». Оно исполняется из **копии правил у приёмника**: добавить его только
  в правила источника недостаточно. Читается через `get_rule_handler` по правилу
  «Конвертация».
- **Получателю пришло удаление живого объекта.** При режиме выгрузки «по условию»
  или «при необходимости» объект перестал проходить отбор регистрации (например,
  отбор по «Проведен» или статусу).
- **Правило регистрации не работает.** Возможные причины:
  - у правила нет признака «валидное»;
  - у объекта в составе плана включена авторегистрация.

  Отключение группы правил не действует (раздел 1). У объекта без правил
  регистрации — все узлы плана.
- **Узел ничего не получает.** Отбор идёт по табличной части узла, а она пуста
  **(вывод)**.
- **Правила не загружаются: «предназначены для другой программы».** В комплект
  положен чужой файл правил обмена: правила корреспондента или правила другой
  конфигурации. Загрузка сверяет имя конфигурации в заголовке.

## 8. Ручной обмен универсальной обработкой — другой исполнитель

Правила проверили ручной выгрузкой и загрузкой обработкой «Универсальный обмен
данными в формате XML» — работает, а обмен через план ведёт себя иначе (или
наоборот). Формат один, исполнители разные; вывод об одном на другой не
переносится. Главные различия:

| Что | Обмен через план | Универсальная обработка |
|---|---|---|
| Способ отбора ветки, выборка и «Отказ» в «перед обработкой правила» | Не исполняются: только очередь узла | Исполняются |
| Признак реквизита «Обязательное» | Поле поиска, как «Поиск» | Обычный реквизит, в поиск не идёт |
| Запись документа | Непроведённым, затем очередь отложенного проведения | Без очереди: как пришёл, или сразу с проведением |
| Регистр соответствий | Найденный по полям объект запоминается, дальше ищется по идентификатору | Нет: каждый раз поиск по полям |
| Объект по ссылке | Только ссылкой, целиком — по условиям раздела 3 | Целиком, если у правила не стоит «не выгружать объекты свойств по ссылкам» |
| Откуда правила загрузки | Копия правил отправителя в приёмнике | Из файла данных |

## 9. Как говорить с человеком

- Различай: «так написано в правилах» (видно инструментами), «так исполняет
  БСП» (этот справочник) и «так произошло в базе» (только протокол обмена,
  журнал регистрации или прогон на тестовой базе).
- Пункт с пометкой «вывод» называй выводом, а не фактом.
- Замечание `check_rules` — повод прочитать место в правилах, а не приговор. В
  нём сказано, когда это штатно.
