# База знаний: как читать правила обмена через rules-mcp

Этот файл подключается в Open WebUI как «Знания» к модели с
[системной подсказкой](PROMPT.md). Он объясняет, что умеет каждый инструмент, в
каком порядке их звать и как не ошибиться при чтении правил обмена
«Конвертации данных 2.0».

---

## 1. Инструменты

| Инструмент | Когда звать |
|---|---|
| `exchange_overview` | Не знаешь направление или точное имя документа. Без направления — список направлений; с направлением — документы и процессы |
| `trace_document` | Первым делом по любому документу: регистрация (а если правил регистрации нет — попадает ли объект в очередь по составу плана), ветки выгрузки, вызываемые правила конвертации и где стоит каждый вызов (обработчик и строка), документы приёмника, каскады (и какие из них только ссылкой), вызовы через общие алгоритмы с обеими строками цепочки, откуда у ветки метки процессов, замечания проверки по ветке и правилам, общие обработчики конвертации |
| `get_rule_handler` | Полный текст обработчика с номерами строк, страницами. Без имени обработчика — перечень обработчиков и их длина, включая обработчики реквизитов и табличных частей. С кодом реквизита или табличной части — их обработчик (у реквизита их до трёх: перед, при и после выгрузки). Правило «Конвертация» — общие события всей конвертации |
| `get_rule_queries` | Запросы обработчика: пакет по частям, временные таблицы, от чего каждая зависит, параметры, какому результату пакета какая переменная присвоена |
| `get_conversion_rule` | Карточка правила конвертации: признаки (синхронизация по идентификатору, «не замещать», «не создавать, если не найден»…), какой реквизит куда переносится, поля поиска, табличные части, каскады в подчинённые правила, у каких реквизитов и табличных частей свои обработчики и их коды, замечания проверки |
| `search_rules` | Где вообще упоминается реквизит, правило или слово. Даёт адреса: правило, обработчик, номер строки. Отбор по правилу понимает код, наименование или имя объекта |
| `check_rules` | Проверка правил без конфигураций: несуществующие алгоритмы и правила, повторы кодов, ветки, которые при обмене через план не срабатывают или срабатывают не так, правила, которые ничем не вызываются, объекты, уходящие только ссылкой, формы поиска, дающие дубли. У замечания — адрес для чтения и чем оно грозит |
| `receiver_fields` | Что правила ждут от конфигурации приёмника — для сверки с настоящим составом объекта |
| `refresh_rules` | Забрать свежие правила из репозитория, не дожидаясь часа. Вызывай, когда человек просит обновить правила или говорит, что выложил новые |

Правило можно назвать кодом, наименованием или именем объекта. Если подходит
несколько, инструмент не выбирает сам, а перечисляет кандидатов — выбери код.
То же с реквизитом: если имя приёмника в правиле повторяется (например, в шапке
и в табличной части), инструмент попросит код реквизита.

Каждый ответ несёт версию правил: ветку и коммит. Её надо называть в ответе
человеку.

**Человек говорит, что свежих правил не видно.** Вызови `refresh_rules` и
покажи из ответа «версию правил» и «внимание», если оно есть. Дальше:
- есть «внимание» — перескажи его: что не так и с какой папкой;
- «без версии (каталог не под git)» — сервис не подключён к репозиторию, это
  настройка сервера, вопрос к администратору;
- ветка или коммит не те, что ждёт человек, — правила выложены в другую ветку.
  Сервис читает только одну, новые правила должны быть влиты в неё;
- коммит последний, а направления нет — папка лежит не прямо в каталоге правил
  или файл назван не `ExchangeRules.xml`.

Настроек сервера ты не видишь — названий не придумывай, отправляй к README
сервиса, раздел «Как выкладывать новые правила».

## 2. Порядок вызова для типовых вопросов

**«Что происходит с документом X при обмене?»**
`trace_document` → по интересным веткам `get_rule_handler` → при необходимости
`get_conversion_rule` по вызываемым правилам.

**«При каких условиях ветка выбирает правило конвертации Y?»**
`trace_document` (ветка и строка вызова правила — у каждого вызываемого правила
указано, в каком обработчике и на какой строке он стоит) → `get_rule_handler` по
этому обработчику целиком → `get_rule_queries`, если условие проверяет результат
запроса. Если правило задано в свойствах ветки, а не вызовом в коде, строки у
него нет — так и написано.

**«Чем заполняется реквизит Z у приёмника?»**
`get_conversion_rule` (есть ли у реквизита обработчик, его код, из какого
реквизита источника он идёт) → `get_rule_handler` с кодом реквизита.

**«Почему у приёмника пустое поле?»**
`receiver_fields` → сверка с конфигурацией приёмника (раздел 7) →
`get_conversion_rule` → обработчик реквизита, если он есть.

**«Почему у приёмника задваивается объект (или сливается с чужим)?»**
`check_rules` с правилом конвертации объекта (проверки «поиск: …») →
`get_conversion_rule` (признаки, поля поиска) → `get_rule_handler` с
обработчиком «ПоследовательностьПолейПоиска», если он есть. Как приёмник ищет
объект — справочник «Поведение обмена БСП», раздел 4.

**«Почему справочник пришёл пустым?»**
`check_rules` — нет ли у его правила замечания «только ссылкой»: тогда уходят
только поля поиска, остальные реквизиты не переносятся. Условия, при которых
объект уходит целиком, — справочник «Поведение обмена БСП», раздел 3.

**«Почему ветка выгрузки не срабатывает?»**
`trace_document` — поле «регистрация» (объекта может не быть ни в правилах
регистрации, ни в составе плана) и «замечания проверки» ветки (вторая ветка на
тот же тип, неисполняемый отбор).

**«Что в правилах сломано?»**
`check_rules` по направлению → ошибки читать по адресам через
`get_rule_handler`. Замечание в алгоритме, который никто не вызывает, на обмен
не влияет — так и помечено.

**«При каких условиях документ регистрируется?»**
`trace_document` (отборы регистрации) → `search_rules` с отбором по правилу —
правило регистрации можно назвать именем документа → `get_rule_handler` по
найденному обработчику. Если у документа несколько правил регистрации, отбор
по имени документа ищет по всем.

## 3. Полнота ответа

- Если в ответе есть «следующая строка», показано не всё. Повторный вызов с этим
  номером строки даёт продолжение без пропусков и нахлёстов.
- Номер строки из поиска совпадает с номером при чтении. Можно сразу читать
  нужный кусок, но условия, внутри которых стоит строка, начинаются выше —
  читай от начала обработчика или хотя бы от начала охватывающего блока.
- Поиск не показывает закомментированные строки. При чтении обработчика они
  видны — не принимай их за действующий код.
- Поиск ограничен числом попаданий; если в ответе сказано, что он обрезан по
  лимиту, сужай отбором по направлению, виду правила, правилу или обработчику.

## 4. Как читать пакетный запрос

- Пакет — несколько запросов в одном тексте, разделённых точкой с запятой.
  Нумерация с нуля: первый запрос пакета — нулевой.
- Запрос, который удаляет временную таблицу, тоже занимает свой номер. Номера
  после него не сдвигаются.
- Запрос с «ПОМЕСТИТЬ» создаёт временную таблицу. Следующие запросы пакета
  могут её читать — инструмент показывает, какие таблицы от каких зависят.
- Выполнение пакета возвращает массив результатов, по одному на каждый запрос.
  Запись вида «Результат[3]» — это результат запроса пакета номер 3.
  Инструмент сам сопоставляет такие записи с частями пакета и показывает, какой
  переменной какой результат присвоен.
- Если номер в скобках вычисляется («РезультатСборка[Количество − 1]»),
  инструмент его не угадывает, а выносит отдельно. Считай сам по коду и отметь,
  что посчитал вручную.
- Одна переменная запроса бывает использована в обработчике несколько раз.
  Каждое новое задание текста — новый запрос; параметры и выполнение
  относятся к ближайшему заданию текста выше.

### Когда текст запроса неполный

Инструмент извлекает текст, только если он написан в коде одной строкой-литералом.
Неполным он помечает запрос, если:

- текст собран из кусков, например через соединение массива строк;
- текст взят из переменной, значение которой задано вне обработчика;
- после задания текст дописывается или в нём что-то заменяется — выполняется
  уже другой текст.

В этих случаях инструмент **ничего частичного не отдаёт**. Сборку по кусочкам
он не делает сознательно: собранный текст выглядит достоверно, а проверить его
нечем. Читай обработчик и собирай сам, помечая, что собрал вручную.

Бывает и невидимый случай: объект запроса передан в процедуру или общий
алгоритм, и текст меняют там. В обработчике следов не остаётся.

## 5. Прямые и каскадные вызовы

- **Прямой вызов** — ветка выгрузки (или общий алгоритм, который она вызывает)
  сама вызывает правило конвертации.
- **Каскадный** — правило конвертации переносит реквизит через подчинённое
  правило, а то создаёт у приёмника ещё один документ. В ветке выгрузки такого
  вызова не видно. `trace_document` показывает каскады в списке документов
  приёмника с пометкой «каскад из …».
- Источник каскадного правила — значение реквизита, который его вызвал, а не
  сам выгружаемый документ.
- По умолчанию значение реквизита уходит **только ссылкой** — полями поиска.
  Документ, на который ссылается реквизит, этим обменом целиком не создаётся,
  если его не выгружают явно. `trace_document` пишет такие каскады отдельно:
  «каскадом только ссылкой», а в документах приёмника — «только ссылка, документ
  не создаётся».

## 6. Разобранный пример: УПП → ЕРП, ветка «РеализацияТоваровУслуг»

Цифры и номера строк — по версии правил на момент написания; сверяй с текущими
ответами инструментов.

**Что вызывается.** `trace_document` показывает двенадцать правил конвертации,
которые вызывает ветка. Среди них интересующие:
«РеализацияТоваровУслуг_ПеремещениеТоваров», «ПеремещениеТоваровММ_ПеремещениеТоваров»,
«РТиУ_ВнПотребление». Правила «РТиУ_ПеремещениеТоваров» среди прямых вызовов
нет: оно вызывается каскадом из «РТиУ_ВнПотребление» через реквизит
«ДокументОснование».

**Где условия.** Все три прямых вызова стоят в обработчике «ПередВыгрузкойОбъекта»
(841 строка): на строках 430, 448 и 523. Второй обработчик ветки,
«ПередОбработкойПравила» (1276 строк), готовит данные.

**Документ подменяется результатом запроса.** В начале обработчика выполняется
пакет из десяти запросов. На строке 419 выгружаемый документ заменяется набором
полей из нулевого результата пакета. Поэтому условие на строке 425 — «функциональный
блок равен ПеремещениеТоваров» — проверяет не реквизит документа, а колонку
запроса. Что в этой колонке, видно только в тексте нулевого запроса пакета.

**Вызов 1, строка 430.** «РеализацияТоваровУслуг_ПеремещениеТоваров» вызывается,
когда документ не отсеян (результаты шапки и товаров не пусты, строка 411) и
функциональный блок равен «ПеремещениеТоваров». Перед вызовом склад-отправитель,
подразделение и товары подменяются (строки 426–428) — значения приходят не из
документа.

**Вызов 2, строка 448.** «ПеремещениеТоваровММ_ПеремещениеТоваров» стоит внутри
той же ветки, но источником ему служит **не реализация, а связанное перемещение**:
на строке 436 объект заново собирается из третьего результата пакета
(«РезультатПеремещение»), товары — из четвёртого («РезультатТоварыПеремещение»).
Дополнительное условие — третий результат не пуст (строка 432). Пометка
удаления и признак «проведён» перед вызовом пересчитываются (строки 441–446).
Это пример того, как правило, стоящее в ветке реализации, получает на вход
другой документ.

**Вызов 3, строка 523.** «РТиУ_ВнПотребление» — в ветке «функциональный блок
равен СписаниеТоваров_Инвентаризация» (строка 498), при непустых товарах. Перед
вызовом в объект кладётся копия исходного документа как «ДокументОснование»
(строки 516–517), и именно по этому реквизиту «РТиУ_ВнПотребление» каскадом
вызывает «РТиУ_ПеремещениеТоваров». Иначе вызывается правило удаления
(строка 527).

**Подвохи этого обработчика.**
- Разметка областей не отражает вложенность: на строке 450 область закрывается
  внутри ветки, до следующего «ИначеЕсли».
- На строке 493 закомментирована целая ветка по блоку «ВГОКомиссия».
  `trace_document` всё равно числит этот процесс за веткой, потому что метку он
  берёт и из вызываемых правил. Откуда метка, он показывает сам: рядом со
  списком процессов есть разбивка — какие метки у ветки свои, а какие пришли от
  вызываемых правил и от каких. «ВГОКомиссия» там значится пришедшей от правила
  «РеализацияТоваровУслуг_ПередачаТоваровХранителю», а не своей. Пришедшая
  метка — подсказка, где искать, а не доказательство, что такая выгрузка
  действует: действует ли она, видно только в обработчике ветки.
- На строке 406 номер результата пакета вычисляется — инструмент его не угадывает.
- Запрос в «ПередОбработкойПравила» собран из шести кусков соединением массива
  (строка 1238) — инструмент пометит его неполным. Временные таблицы
  «ВТ_Перемещения», «ВТ_ПеремещенияПредв», «ВТ_Товары_Перемещения» создаются
  именно там. Их назначение определяется текстом запроса, не именем.

**Чего сервис здесь не делает сам.** Он не выдаёт «стек условий» автоматически
и не строит запрос для консоли. Разбор условий делается по полному тексту
обработчика, а запрос для консоли собирается из извлечённых частей пакета и
текста обработчика — с пометкой, что собран вручную.

## 7. Сверка с конфигурацией (rlm-tools-bsl)

Правила обмена ссылаются на реквизиты, типы, процедуры и значения двух
конфигураций. Сам сервис правил конфигураций не видит. Их видит второй сервер,
rlm-tools-bsl: в нём загружены исходники УПП, ЕРП, Розницы и Итилиума. Серверы
друг о друге не знают — связывает их модель.

### Как работать со вторым сервером

- **Какая конфигурация.** Определяется стороной направления из ответа сервиса
  правил: «УПП → ЕРП» — источник УПП, приёмник ЕРП. Реквизиты приёмника
  смотрятся в приёмнике. Процедуры, запросы и значения из обработчиков — там,
  где обработчик выполняется: обработчики регистрации, веток выгрузки, правил
  и реквизитов до загрузки — в источнике; обработчики «при загрузке» и «после
  загрузки» правила конвертации — в приёмнике.
- **Имя проекта.** Список конфигураций — `rlm_projects` (действие «список»).
  Имена там заданы администратором и могут не совпадать с «УПП» и «ЕРП»
  дословно — выбери подходящий по названию и описанию. Не уверен — спроси
  человека. Проекты не регистрируй и не меняй: это действие под паролем, оно для
  человека.
- **Сессия.** `rlm_start` с именем проекта и коротким описанием задачи. Сессия
  одна на конфигурацию на весь разговор: для сверки источника и приёмника
  понадобятся две. В конце — `rlm_end` для каждой.
- **Справка.** Сразу после открытия вызови `rlm_help` — сервер сам этого
  требует. Точные сигнатуры помощников — `rlm_help` с их именами. Не угадывай,
  что возвращает помощник: сначала справка.
- **Работа.** `rlm_execute` выполняет короткий сценарий на Python, в котором
  доступны помощники песочницы. В ответ приходит только то, что сценарий
  напечатал: печатай сводку, а не всё подряд. Несколько связанных вопросов
  складывай в один сценарий.
- **Полнота.** Ответы второго сервера тоже бывают неполными: у многих есть
  признак усечения или частичного ответа, а без построенного индекса часть
  поисков работает хуже. Как читать эти признаки — `rlm_help` с разделом
  «coverage». Пустой ответ помощника ещё не значит, что объекта нет: перед
  выводом «нет» поищи полнотекстом (`git_search` или `safe_grep`).

### Сценарий 1. Приёмник: чего нет, что переименовано, у чего другой тип

Это тихая потеря данных: обмен не падает, но значение до приёмника не доходит.

1. `receiver_fields` по документу — какие реквизиты и табличные части правила
   заполняют у объекта приёмника и каких типов. Для справочника — повторный вызов
   с его именем.
2. Во втором сервере, в конфигурации приёмника, — настоящий состав того же
   объекта. Помощник `get_object_full_structure` отдаёт реквизиты, табличные
   части с колонками и типы за один вызов; `find_attributes` с именем объекта —
   плоский список реквизитов с типами.
3. Сравни построчно: реквизита нет совсем; есть с похожим именем
   (переименован); есть, но другого типа; реквизит в правилах в шапке, а в
   конфигурации в табличной части, или наоборот.

Имена типов в конфигурации могут быть записаны по-английски
(«CatalogRef.Номенклатура» против «СправочникСсылка.Номенклатура» в правилах) —
это одно и то же, не расхождение. Составной тип в правилах может быть уже, чем в
конфигурации, — это тоже не ошибка; ошибка — когда тип из правил в конфигурации
не допускается.

Ответ второго сервера о составе объекта берётся из его индекса, а индекс может
отставать от исходников. Если реквизита «нет», а расхождение важное, перепроверь
чтением описания объекта (`parse_object_xml`) или полнотекстом.

### Сценарий 2. Поля запроса в источнике

Прежде чем отдать аналитику запрос для консоли, проверь по конфигурации
источника, что все таблицы и поля в нём существуют: регистры, документы,
справочники, их реквизиты и табличные части. Состав объекта — те же помощники,
что в сценарии 1, но в конфигурации источника. Поле, которого нет, — либо
ошибка в правилах, либо запрос правил давно не выполнялся в этом виде; в обоих
случаях это находка, а не повод поправить запрос молча.

### Сценарий 3. Процедуры общих модулей источника

Обработчики зовут процедуры и функции конфигурации-источника — общих модулей,
модулей менеджеров. Их текста в правилах нет. Пример из разобранного случая:
копию документа для реквизита «ДокументОснование» ветка «РеализацияТоваровУслуг»
делает процедурой общего модуля УПП (строка 516 обработчика
«ПередВыгрузкойОбъекта»). Что именно попадёт в копию, из правил не видно.

Как прочитать: `find_definition` с именем процедуры (подсказкой можно указать
модуль) — где она определена; `read_procedure` с найденным путём и именем —
текст процедуры с номерами строк. Если процедура зовёт другие — читай и их, пока
не станет ясно, что она делает с данными.

### Сценарий 4. Значения в условиях

Условие в обработчике сравнивает с перечислением («Перечисления.X.Значение») или
с предопределённым элементом («Справочники.X.Имя»). Существует ли такое
значение, видно только в конфигурации: `find_enum_values` с именем перечисления,
`find_predefined` с именем объекта. Смотри в той конфигурации, где выполняется
обработчик. Значения нет — обработчик завершится ошибкой, как только выполнение
дойдёт до этого места. Это находка, даже если ошибок в работе обмена не видно:
значит, до этого места выполнение не доходит.

### Что писать в ответе

- Расхождение правил и конфигурации называй отдельным пунктом: что в правилах,
  что в конфигурации, к чему это приводит.
- Если второй сервер не ответил, нужной конфигурации в нём нет или ответ
  помечен неполным — так и напиши. Вывод «всё сходится» без сверки не делай.

## 8. Частые ошибки при работе с инструментами

Здесь только ошибки чтения ответов инструментов. Ошибки разбора самих правил —
когда правила ведут себя не так, как выглядят, — разобраны отдельно, в
справочнике ловушек.

| Ошибка | Как правильно |
|---|---|
| Вывод по одной строке поиска | Прочитать обработчик целиком, выписать все охватывающие условия |
| «Документ регистрируется — значит, уйдёт этим правилом» | Регистрация только ставит в очередь. Правило выбирает ветка выгрузки |
| «В ветке нет вызова правила — значит, она его не вызывает» | Проверить вызовы через общие алгоритмы в ответе `trace_document` |
| «Ветка с произвольным отбором выгружает то, что отбирает её запрос» | При обмене через план отбор не исполняется: ветку запускают объекты её типа из очереди. Смотри «регистрацию» и «замечания проверки» в `trace_document` |
| «У документа две ветки — работают обе» | Для типа работает только первая включённая ветка; вторая помечена в «замечаниях проверки» |
| «В начале обработчика „Отказ = Истина“ — значит, ветка выключена» | В «перед обработкой правила» «Отказ» при обмене через план ничего не отменяет |
| «Каскад на документ — значит, у приёмника появится ещё один документ» | Если помечено «только ссылкой», документ этим обменом не создаётся |
| Замечание `check_rules` — сразу вывод | Сначала прочитать место по адресу; в замечании сказано, когда это штатно |
| Достроить неполный запрос и выдать как готовый | Сказать, что текст неполный; собранное вручную помечать |
| Не назвать версию правил | Ветка и коммит — в каждом ответе |
| «Процесс числится за веткой — значит, выгрузка по нему действует» | Посмотреть, своя это метка ветки или пришла от вызываемого правила, и проверить обработчик |
| «Правила пишут в этот реквизит — значит, он у приёмника есть» | Сверить с конфигурацией приёмника во втором сервере |
| «Сверить не удалось, но наверняка всё сходится» | Сказать, что сверки не было и почему |
